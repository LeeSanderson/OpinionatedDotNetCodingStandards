## What to build

Add a test for rule **MA0227** — *Avoid using 'Enumerable.Contains' on a set* — from the
`Meziantou.Analyzer` analyzer.

`Enumerable.Contains` only delegates to the source's own O(1) lookup when the source implements
`ICollection<T>` **for the searched value's type**. The rule reports the two shapes where that
fast path is bypassed and the call silently degrades to a linear scan of the set:

1. **A comparer is passed** — `set.Contains(value, StringComparer.Ordinal)` has no `ICollection<T>`
   fast path at all and always enumerates.
2. **The searched value's type differs from the set's element type** — e.g. searching for an
   `object` in a `HashSet<string>`; the covariant call cannot use the set's hash lookup.

This rule is configured as **`warning`** in
`packages/Opinionated.DotNet.CodingStandards/pkgsrc/config/analyzers/Analyzer.Meziantou.Analyzer.editorconfig`,
so it surfaces as a SARIF **error** — assert with `HasError`.

## How to implement the test

Add a `[Fact]` to `MeziantouAnalyzersCoreShould.cs` (currently ~441 lines — well under the
1000-line split threshold, so add it to the end of the existing class):

```csharp
[Fact]
[RuleDoc("MA0227", "Avoid using 'Enumerable.Contains' on a set",
    HelpLink = "https://github.com/meziantou/Meziantou.Analyzer/blob/main/docs/Rules/MA0227.md")]
public async Task ProhibitEnumerableContainsOnASet()
{
    using var project = await CreateProjectBuilderAsync();
    await project.AddFileAsync("Program.cs", """
        using System;
        using System.Collections.Generic;
        using System.Linq;
        namespace test;
        public class C
        {
            public bool M(HashSet<string> set, string value) => set.Contains(value, StringComparer.Ordinal);
        }
        public static class Program { public static int Main() => 0; }
        """);
    var buildOutput = await project.BuildAndGetOutputAsync();

    buildOutput.HasError("MA0227").ShouldBeTrue();
}
```

### Watch out for

- **`set.Contains(value)` with no comparer does NOT trigger the rule** — that binds to
  `HashSet<string>.Contains`, the O(1) instance method, which is the recommended fix. The overload
  with a comparer is what forces `Enumerable.Contains`.
- `using System.Linq;` is required for the extension method to bind at all. Without it the code
  will not compile and the build will fail for the wrong reason.
- If the comparer shape does not fire, use the second documented shape instead — the type-mismatch
  one:
  ```csharp
  public bool M(HashSet<string> set, object value) => set.Contains(value);
  ```
  Here `Enumerable.Contains<object>` is selected over `HashSet<string>.Contains(string)` because
  the argument is `object`, so the set's lookup is bypassed. Either shape is an acceptable test —
  pick whichever actually fires.
- The rule also covers `ISet<T>`, `IReadOnlySet<T>` and `IImmutableSet<T>` receivers, so those are
  fallbacks if `HashSet<T>` specifically does not fire.

## Confounder playbook (exhaust before marking untestable)

Everything this rule needs is in the BCL, so it is expected to be straightforwardly testable. If it
does not fire, work through the standard playbook in AGENTS.md in order:

1. **Add a package reference** — not applicable; `HashSet<T>` and LINQ are in the BCL.
2. **Use stub types** — not applicable.
3. **Pin `LangVersion=12`** — worth trying here specifically: C# 13 overload routing can redirect a
   `Contains` call to a different overload than the analyzer matches (this is the known
   `CA1842`/`CA1843` failure mode).
4. **Set `ignore_internalsvisibleto=true`** — try if the rule appears friend-assembly sensitive.
5. **Check `EnforceOnBuild`** in the analyzer source (`EnforceOnBuild.Never` is structurally silent
   at build).
6. **Check the reporting analyzer's assembly path** (`src/Features/` = IDE-only).
7. **Check the mscorlib gate** — not applicable to a Meziantou rule.

Only move the rule to `UntestableRules.cs` after exhausting all of the above.
