## How the rule works

`MA0240` is the syntax-level counterpart of `BannedSymbols.txt` / `RS0030`. It reports syntax
listed in a `BannedSyntaxes.txt` additional file, with the message given for that entry. The
analyzer is `DoNotUseBannedSyntaxAnalyzer`
(https://github.com/meziantou/Meziantou.Analyzer/blob/main/src/Meziantou.Analyzer/Rules/DoNotUseBannedSyntaxAnalyzer.cs).

It is **enabled by default but does nothing until the project has a banned syntax file** — that is
the one and only gate. The analyzer reads additional files named `BannedSyntaxes.txt` or
`BannedSyntaxes.*.txt`. Meziantou's own `build/Meziantou.Analyzer.props` also auto-adds the closest
`BannedSyntaxes.txt` found in the project folder or a parent, but the test should pass
`additionalFiles: ["BannedSyntaxes.txt"]` explicitly rather than rely on that MSBuild directory
walk from a temp directory.

File format — one query per line, optionally `; message`; `#` starts a comment. A query is either
a case-sensitive `Microsoft.CodeAnalysis.CSharp.SyntaxKind` member name (optionally preceded by
`//`), or an XPath 1.0 query over the syntax tree:

```text
GotoStatement; Use structured control flow instead
//ClassDeclaration/ParameterList; Do not use primary constructors
```

The diagnostic message is `The syntax '<kind>' is banned: <message>`.

## How to implement the test

Add a `[Fact]` to
`tests/Opinionated.DotNet.CodingStandards.Tests/MeziantouAnalyzers/MeziantouAnalyzersCoreShould.cs`.
`BannedApiAnalyzersShould.ReportDuplicateBannedSymbolEntry` is the existing precedent for the
`additionalFiles` + `AddFileAsync` pairing — mirror it.

```csharp
[Fact]
[RuleDoc("MA0240", "Do not use banned syntax",
    HelpLink = "https://github.com/meziantou/Meziantou.Analyzer/blob/main/docs/Rules/MA0240.md")]
public async Task ProhibitBannedSyntax()
{
    using var project = await CreateProjectBuilderAsync(additionalFiles: ["BannedSyntaxes.txt"]);
    // MA0240 is enabled by default but inert until the project supplies a BannedSyntaxes.txt
    // additional file, so the file IS the trigger. A bare SyntaxKind name is the cheapest form
    // of query (matched in a single pass, no XPath, no semantic model).
    await project.AddFileAsync("BannedSyntaxes.txt", "GotoStatement; Use structured control flow instead");
    await project.AddFileAsync("Program.cs", """
        namespace test;
        public class C
        {
            public int M()
            {
                goto end;
            end:
                return 0;
            }
        }
        public static class Program { public static int Main() => 0; }
        """);
    var buildOutput = await project.BuildAndGetOutputAsync();

    buildOutput.HasError("MA0240").ShouldBeTrue();
}
```

Note the chosen sample code must not trip a *different* rule so badly that the build never reaches
the SARIF write — but `BuildAndGetOutputAsync` reads the ErrorLog regardless of exit code, and
`HasError("MA0240")` only asserts on that one rule ID, so unrelated diagnostics from the `goto`
(e.g. a Sonar or IDE rule that also dislikes `goto`) do not invalidate the test. If a co-firing
rule turns out to make the build fail before the analyzer runs, prefer a banned syntax kind that
no other bundled rule objects to (for example ban `//ClassDeclaration/ParameterList` and declare a
primary constructor) rather than adding `NoWarn`.

## Confounder playbook (exhaust before marking untestable)

Work through these in order:

1. **Supply the additional file** — this is almost certainly the whole job for `MA0240`. If the
   rule does not fire, first confirm the file actually reached the compiler as an additional file:
   the `AdditionalFiles` item must be present *and* the file must exist on disk before
   `BuildAndGetOutputAsync` runs. Also confirm the `SyntaxKind` name is spelled exactly (it is
   case-sensitive) — a typo silently produces `MA0241` instead of `MA0240`.
2. **Add a package reference** if the rule guards on types in an external package. Not applicable
   here — the rule is purely syntactic.
3. **Use stub types** if the rule merely requires a type to exist in the compilation. Not
   applicable here.
4. **Pin `LangVersion=12`** if C# 13 might route single-argument calls to a new `ReadOnlySpan`
   overload that the analyzer can't match. Not applicable here.
5. **Set `ignore_internalsvisibleto=true`** if the rule is friend-assembly-sensitive. Not
   applicable here.
6. **Check `EnforceOnBuild` in Roslyn source** — not applicable; this is a Meziantou rule, not an
   IDE rule, and the regenerated editorconfig reports `Enabled: True, Severity: warning`.
7. **Check the reporting analyzer's assembly path** — `DoNotUseBannedSyntaxAnalyzer` is in
   `src/Meziantou.Analyzer/Rules/`, which ships in the analyzer assembly and runs at build.

Only move the rule to `UntestableRules.cs` after exhausting all of the above.
