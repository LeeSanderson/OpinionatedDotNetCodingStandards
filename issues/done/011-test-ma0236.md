## What to build

Add a test for rule **MA0236** — *The payload written by an EventSource event method must use the
order of its parameters* — from the `Meziantou.Analyzer` analyzer.

This is the ordering counterpart of `MA0235`: the `WriteEvent` call passes exactly the method's
parameters, but in a different order than they are declared. The manifest is built from the
declaration order, so every field on the wire is decoded into the wrong slot — and when the types
happen to be compatible, nothing fails loudly.

This rule is configured as **`warning`** in
`packages/Opinionated.DotNet.CodingStandards/pkgsrc/config/analyzers/Analyzer.Meziantou.Analyzer.editorconfig`,
so it surfaces as a SARIF **error** — assert with `HasError`.

## How to implement the test

Add a `[Fact]` to `MeziantouAnalyzersEventSourceShould.cs` (created by issue 001):

```csharp
[Fact]
[RuleDoc("MA0236", "The payload written by an EventSource event method must use the order of its parameters",
    HelpLink = "https://github.com/meziantou/Meziantou.Analyzer/blob/main/docs/Rules/MA0236.md")]
public async Task RequireWrittenPayloadToUseParameterOrder()
{
    using var project = await CreateProjectBuilderAsync();
    await project.AddFileAsync("Program.cs", """
        using System.Diagnostics.Tracing;
        namespace test;
        public sealed class MyEventSource : EventSource
        {
            [Event(1)]
            public void Started(string message, int count) => WriteEvent(1, count, message);
        }
        public static class Program { public static int Main() => 0; }
        """);
    var buildOutput = await project.BuildAndGetOutputAsync();

    buildOutput.HasError("MA0236").ShouldBeTrue();
}
```

### Watch out for

- **Keep the class `sealed`** — otherwise `MA0226` fires as well.
- **Keep the written id matching the `[Event]` id** (both `1` above) so `MA0234` does not fire.
- **Every parameter must still be present exactly once** — that is what distinguishes this from
  `MA0235` (issue 010), which is the *missing/substituted* argument case. Only the order differs.
- Use parameters of two different types (`string` and `int` above) so the swapped call still
  compiles: `WriteEvent(int, object, object)` / `WriteEvent(int, params object[])` accepts both.

## Confounder playbook (exhaust before marking untestable)

`System.Diagnostics.Tracing.EventSource` is in the BCL on `net10.0`, so no `PackageReference` is
needed and this rule is expected to be straightforwardly testable. If it does not fire, work
through the standard playbook in AGENTS.md in order:

1. **Add a package reference** — not applicable; `EventSource` is in the BCL.
2. **Use stub types** — not applicable; the real `EventSource` is available.
3. **Pin `LangVersion=12`** — worth trying: `WriteEvent` has many overloads (including
   `params object[]`), and C# 13 routing can select a different one than the analyzer matches.
4. **Set `ignore_internalsvisibleto=true`** — try if the rule appears friend-assembly sensitive.
5. **Check `EnforceOnBuild`** in the analyzer source (`EnforceOnBuild.Never` is structurally silent
   at build).
6. **Check the reporting analyzer's assembly path** (`src/Features/` = IDE-only).
7. **Check the mscorlib gate** — not applicable to a Meziantou rule.

If `MA0235` fires here instead of `MA0236`, the analyzer is treating a reorder as a mismatch — try
two same-typed parameters (`string first, string second` written as `WriteEvent(1, second, first)`)
so the argument *set* is provably identical and only the order can be at fault.

Only move the rule to `UntestableRules.cs` after exhausting all of the above.
