## What to build

Add a test for rule **MA0220** — *The configured regular expression is not valid* — from the
`Meziantou.Analyzer` analyzer.

Unlike most rules, `MA0220` does not analyse source code. It validates **`.editorconfig` option
values**: some Meziantou rules take a regular expression as configuration, and when the value is
not a valid regex the option is silently ignored. `MA0220` reports those invalid values so a typo
does not quietly change a rule's behaviour.

The options validated by this rule (per the upstream docs) are:

- `MA0003.excluded_methods_regex`
- `MA0104.namespaces_regex`

This rule is configured as **`warning`** (also its upstream default), so it surfaces as a SARIF
**error** — assert with `HasError`.

## How to implement the test

This test needs a **local `.editorconfig`** carrying a deliberately broken regex. `ProjectBuilder`
supports this via `AddFileAsync(".editorconfig", ...)` — see the existing `CA1852` test in
`CodeAnalysisRules/CodeAnalysisRulesPerformanceModernShould.cs` and the `IDE2006` test in
`CodingStandards/CodingStandardsStyleShould.cs` for the established pattern.

```csharp
[Fact]
[RuleDoc("MA0220", "The configured regular expression is not valid",
    HelpLink = "https://github.com/meziantou/Meziantou.Analyzer/blob/main/docs/Rules/MA0220.md")]
public async Task ProhibitInvalidConfiguredRegularExpression()
{
    using var project = await CreateProjectBuilderAsync();

    // MA0220 validates .editorconfig option values rather than source code. '[' is an
    // unterminated character class, so the configured option cannot be compiled to a Regex.
    await project.AddFileAsync(
        ".editorconfig",
        """
        [*.cs]
        MA0104.namespaces_regex = [
        """);
    await project.AddFileAsync("Program.cs", """
        namespace test;
        public static class Program { public static int Main() => 0; }
        """);
    var buildOutput = await project.BuildAndGetOutputAsync();
    buildOutput.HasError("MA0220").ShouldBeTrue();
}
```

### Watch out for

- **The option key has no `dotnet_diagnostic.` prefix.** Upstream's own example writes it bare as
  `MA0104.namespaces_regex = [`. If the diagnostic does not fire, try the
  `dotnet_diagnostic.MA0104.namespaces_regex` and `dotnet_code_quality.` prefixed spellings before
  concluding anything, and check the analyzer source
  (`InvalidRegexConfigurationAnalyzer.cs`) for the exact key it reads.
- Try the other validated option (`MA0003.excluded_methods_regex`) as a second shape if the first
  does not fire.
- `MA0104` itself is configured `none` in this package. That should not matter — `MA0220` reports
  on the *configuration value*, not on `MA0104` firing — but if the diagnostic does not appear,
  confirm whether the analyzer only validates options for enabled rules. If it does, pick a
  validated option whose owning rule is enabled, or set the owning rule's severity in the same
  local `.editorconfig`.
- The rule reports at the `.editorconfig` location, not in `Program.cs`. `BuildOutputFile` matches
  on rule ID, so this does not affect the assertion.
