## What to build

Add a test for rule **MA0235** — *The payload written by an EventSource event method must match its
parameters* — from the `Meziantou.Analyzer` analyzer.

`EventSource` builds the event's manifest from the *method signature* but writes whatever the
`WriteEvent` call passes. If the call omits, adds or substitutes an argument, the payload on the
wire does not match the declared schema and consumers mis-decode it.

This rule is configured as **`warning`** in
`packages/Opinionated.DotNet.CodingStandards/pkgsrc/config/analyzers/Analyzer.Meziantou.Analyzer.editorconfig`,
so it surfaces as a SARIF **error** — assert with `HasError`.

## How to implement the test

Add a `[Fact]` to `MeziantouAnalyzersEventSourceShould.cs` (created by issue 001):

```csharp
[Fact]
[RuleDoc("MA0235", "The payload written by an EventSource event method must match its parameters",
    HelpLink = "https://github.com/meziantou/Meziantou.Analyzer/blob/main/docs/Rules/MA0235.md")]
public async Task RequireWrittenPayloadToMatchParameters()
{
    using var project = await CreateProjectBuilderAsync();
    await project.AddFileAsync("Program.cs", """
        using System.Diagnostics.Tracing;
        namespace test;
        public sealed class MyEventSource : EventSource
        {
            [Event(1)]
            public void Started(string message, int count) => WriteEvent(1, message);
        }
        public static class Program { public static int Main() => 0; }
        """);
    var buildOutput = await project.BuildAndGetOutputAsync();

    buildOutput.HasError("MA0235").ShouldBeTrue();
}
```

### Watch out for

- **Keep the class `sealed`** — otherwise `MA0226` fires as well.
- **Keep the written id matching the `[Event]` id** (both `1` above) so `MA0234` (issue 009) does
  not fire alongside it.
- **Do not simply reorder the parameters** — a payload containing exactly the right arguments in
  the wrong order is `MA0236` (issue 011), a different rule. This test must *omit* (or substitute)
  an argument, not reorder them.
- The dropped parameter (`count`) is deliberately unused in the body. If an unrelated
  "unused parameter" diagnostic also appears, that is harmless — the assertion targets `MA0235`
  specifically.

## Confounder playbook (exhaust before marking untestable)

`System.Diagnostics.Tracing.EventSource` is in the BCL on `net10.0`, so no `PackageReference` is
needed and this rule is expected to be straightforwardly testable. If it does not fire, work
through the standard playbook in AGENTS.md in order:

1. **Add a package reference** — not applicable; `EventSource` is in the BCL.
2. **Use stub types** — not applicable; the real `EventSource` is available.
3. **Pin `LangVersion=12`** — worth trying: `WriteEvent` has many overloads (including
   `params object[]`), and C# 13 routing can select a different one than the analyzer matches.
4. **Set `ignore_internalsvisibleto=true`** — try if the rule appears friend-assembly sensitive.
5. **Check `EnforceOnBuild`** in the analyzer source (`EnforceOnBuild.Never` is structurally silent
   at build).
6. **Check the reporting analyzer's assembly path** (`src/Features/` = IDE-only).
7. **Check the mscorlib gate** — not applicable to a Meziantou rule.

**Any fallback must change the argument COUNT, not just the values.** The investigation pass
confirmed against the shipped Meziantou.Analyzer 3.0.258 assembly that the MA0235 message template
is `"'{0}' writes {1} payload item(s) but the event method declares {2} payload parameter(s)"` — a
pure **arity** check. So substituting one argument for another
(`public void Started(string message) => WriteEvent(1, "literal");`) writes 1 item against 1
declared parameter and will **not** fire. A valid fallback writes an extra item instead:
`public void Started(string message) => WriteEvent(1, message, message);` (writes 2, declares 1).
That arity framing is also why a pure reorder cannot be misattributed here — it keeps the count
equal and belongs to `MA0236`.

Only move the rule to `UntestableRules.cs` after exhausting all of the above.
