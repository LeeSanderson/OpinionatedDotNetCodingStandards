set RespectNullableAnnotations* — from the `Meziantou.Analyzer` analyzer.

## How to implement the test

Add a `[Fact]` to `MeziantouAnalyzers3Should.cs`:

```csharp
[Fact]
[RuleDoc("MA0222", "JsonSourceGenerationOptions should set RespectNullableAnnotations",
    HelpLink = "https://github.com/meziantou/Meziantou.Analyzer/blob/main/docs/Rules/MA0222.md")]
public async Task RequireRespectNullableAnnotationsOnJsonSourceGenerationOptions()
{
    using var project = await CreateProjectBuilderAsync();
    await project.AddFileAsync("Program.cs", """
        namespace test;
        using System.Text.Json.Serialization;

        public sealed class Payload
        {
            public string? Name { get; set; }
        }

        [JsonSourceGenerationOptions]
        [JsonSerializable(typeof(Payload))]
        internal sealed partial class PayloadContext : JsonSerializerContext;

        public static class Program { public static int Main() => 0; }
        """);
    var buildOutput = await project.BuildAndGetOutputAsync();
    buildOutput.HasError("MA0222").ShouldBeTrue();
}
```

The rule fires on a `[JsonSourceGenerationOptions]` attribute that does **not** set
`RespectNullableAnnotations = true`. No `PackageReference` is needed —
`System.Text.Json.Serialization` and `JsonSerializerContext` are in the `net10.0` BCL, and
`RespectNullableAnnotations` has existed on the attribute since .NET 9.

Notes and likely confounders specific to this rule:

- **The System.Text.Json source generator will run** on the `JsonSerializerContext`-derived
  partial class. Generated code can raise unrelated diagnostics. That is fine — the assertion only
  checks for `MA0222` — but if generator errors stop the build before analyzers run, simplify the
  serialized type (a single `string` property is enough) or add the offending IDs to
  `properties: [("NoWarn", "...")]`.
- **A bare `[JsonSourceGenerationOptions]` with no arguments** is the most likely trigger, but the
  analyzer may instead require the attribute to set *some* other property while omitting
  `RespectNullableAnnotations`. If the bare form stays silent, try
  `[JsonSourceGenerationOptions(WriteIndented = true)]`.
- **MA0223 fires on the same attribute** (it wants `RespectRequiredConstructorParameters`). Both
  diagnostics appearing on this snippet is expected and harmless — each test asserts only its own
  rule ID. Do **not** try to write one test covering both; each rule needs its own `[RuleDoc]`.
- `partial class ... : JsonSerializerContext;` requires the context to be `partial`; keep that
  modifier or the generator won't produce the type and the attribute may be discarded.

## Confounder playbook (exhaust before marking untestable)

Work through these in order:

1. **Add a package reference** if the rule guards on types in an external package:
   - Logging rules (`CA1727`, `CA1848`, `CA2253`, `CA2254`, `CA2017`, `CA1873`, `CA2023`):
     add `("Microsoft.Extensions.Logging.Abstractions", "10.0.0")` to `packageReferences`.
   - ASP.NET Core MVC rules (`CA5391`, `CA5395`):
     add `("Microsoft.AspNetCore.Mvc", "2.3.10")` and set
     `properties: [("NuGetAudit", "false"), ("NoWarn", "NU1903;NU1902;CA1515;CA1822")]`.

   For MA0222, nothing extra is required — but if `RespectNullableAnnotations` doesn't resolve,
   confirm the harness really targets `net10.0` before concluding anything.

2. **Use stub types** if the rule merely requires a type to exist in the compilation (no real
   package needed — just declare a matching type with the right name/namespace in `Program.cs`).

3. **Pin `LangVersion=12`** if C# 13 might route single-argument calls to a new `ReadOnlySpan`
   overload that the analyzer can't match (known to affect `CA1842`, `CA1843`). If the
   `partial class X : Y;` semicolon-bodied form trips the language version, fall back to
   `partial class X : Y { }`.

4. **Set `ignore_internalsvisibleto=true`** on `CreateProjectBuilderAsync` if the rule is
   friend-assembly-sensitive (e.g., `CA1852`).

5. **Check `EnforceOnBuild` in Roslyn source** — rules tagged `EnforceOnBuild.Never` are
   structurally silent at `dotnet build` regardless of editorconfig severity. (Applies to `IDE`
   rules only — not relevant for `MA` rules.)

6. **Check the reporting analyzer's assembly path** — if the reporting class lives in a
   `src/Features/` path (not `src/Analyzers/`), it is IDE/LSP-only and cannot run at build time.
   Mark untestable and cite the path.

7. **Check mscorlib gate** — rules that assert `System.String` is in `mscorlib` cannot fire on
   `net10.0` (it lives in `System.Private.CoreLib`). Mark untestable with that explanation.

Only move the rule to `UntestableRules.cs` after exhausting all of the above.
