## What to build

Add a test for rule **MA0230** — *The event name of an EventSource is already used by another
event* — from the `Meziantou.Analyzer` analyzer.

Event names must be unique within an `EventSource`. An event's name **is its method name**, so two
overloads of the same name produce two events with the same name — a manifest ETW cannot build.

This rule is configured as **`warning`** in
`packages/Opinionated.DotNet.CodingStandards/pkgsrc/config/analyzers/Analyzer.Meziantou.Analyzer.editorconfig`,
so it surfaces as a SARIF **error** — assert with `HasError`.

## How to implement the test

Add a `[Fact]` to `MeziantouAnalyzersEventSourceShould.cs` (created by issue 001):

```csharp
[Fact]
[RuleDoc("MA0230", "The event name of an EventSource is already used by another event",
    HelpLink = "https://github.com/meziantou/Meziantou.Analyzer/blob/main/docs/Rules/MA0230.md")]
public async Task ProhibitDuplicateEventName()
{
    using var project = await CreateProjectBuilderAsync();
    await project.AddFileAsync("Program.cs", """
        using System.Diagnostics.Tracing;
        namespace test;
        public sealed class MyEventSource : EventSource
        {
            [Event(1)]
            public void Started() => WriteEvent(1);

            [Event(2)]
            public void Started(string message) => WriteEvent(2, message);
        }
        public static class Program { public static int Main() => 0; }
        """);
    var buildOutput = await project.BuildAndGetOutputAsync();

    buildOutput.HasError("MA0230").ShouldBeTrue();
}
```

### Watch out for

- **The clash must be two overloads of the same method name.** The investigation pass confirmed
  against the shipped Meziantou.Analyzer 3.0.258 assembly that the analyzer does
  `if (!eventNames.Add(method.Name)) ReportDiagnostic(DuplicateEventNameRule, ...)` — it keys on
  the **method name** and never reads `[Event(..., EventName = "...")]` (a raw UTF-16 search for
  the literal `EventName` returns zero hits in the assembly, while `EventAttribute`,
  `NonEventAttribute` and `WriteEvent` all hit). Upstream's own non-compliant example is likewise
  a `Start()` / `Start(string)` overload pair. Two differently-named methods will **not** fire this
  rule no matter what `EventName` says.
- **Keep the class `sealed`** — otherwise `MA0226` fires as well.
- **Give the two events distinct ids** (`1` and `2` above) so `MA0229` (duplicate id, issue 004)
  does not fire alongside this one. The clash must be on the *name* only.
- **Keep each `WriteEvent` id matching its own `[Event]` id, and each payload matching that
  overload's own parameters**, so `MA0234` / `MA0235` do not fire too.

needed and this rule is expected to be straightforwardly testable. If it does not fire, work
through the standard playbook in AGENTS.md in order:

2. **Use stub types** — not applicable; the real `EventSource` is available.
3. **Pin `LangVersion=12`** — only if overload routing on `WriteEvent` looks suspect.
4. **Set `ignore_internalsvisibleto=true`** — try if the rule appears friend-assembly sensitive.
5. **Check `EnforceOnBuild`** in the analyzer source (`EnforceOnBuild.Never` is structurally silent
   at build).
6. **Check the reporting analyzer's assembly path** (`src/Features/` = IDE-only).
7. **Check the mscorlib gate** — not applicable to a Meziantou rule.

Also try adding an explicit `[EventSource(Name = "Test-MyEventSource")]` attribute to the class,
in case the analyzer requires a fully-shaped event source.

Only move the rule to `UntestableRules.cs` after exhausting all of the above.
