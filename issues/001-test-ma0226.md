## What to build

Add a test for rule **MA0226** — *EventSource class should be sealed* — from the
`Meziantou.Analyzer` analyzer.

The rule fires on any type deriving from `System.Diagnostics.Tracing.EventSource` that is not
declared `sealed`. ETW resolves event methods reflectively against the concrete type, so an
unsealed `EventSource` whose subclass adds or overrides event methods produces a manifest that
does not match what is actually written at runtime.

This rule is configured as **`warning`** in
`packages/Opinionated.DotNet.CodingStandards/pkgsrc/config/analyzers/Analyzer.Meziantou.Analyzer.editorconfig`,
so it surfaces as a SARIF **error** — assert with `HasError`.

## How to implement the test

```csharp
[Fact]
[RuleDoc("MA0226", "EventSource class should be sealed",
    HelpLink = "https://github.com/meziantou/Meziantou.Analyzer/blob/main/docs/Rules/MA0226.md")]
public async Task RequireEventSourceClassToBeSealed()
{
    using var project = await CreateProjectBuilderAsync();
    await project.AddFileAsync("Program.cs", """
        using System.Diagnostics.Tracing;
        namespace test;
        public class MyEventSource : EventSource
        {
            [Event(1)]
            public void Started(string message) => WriteEvent(1, message);
        }
        public static class Program { public static int Main() => 0; }
        """);
    var buildOutput = await project.BuildAndGetOutputAsync();

    buildOutput.HasError("MA0226").ShouldBeTrue();
}
```

### Watch out for

- **This is the one EventSource test whose class must NOT be `sealed`** — that is the whole point
  of the rule. Every other test in this file declares its `EventSource` subclass `sealed`
  specifically so that `MA0226` does not fire alongside the rule under test.
- Keep the event method itself correct (`[Event(1)]` matched by `WriteEvent(1, ...)`, payload
  exactly the method's parameters) so no sibling EventSource rule fires and muddies the result.

## Confounder playbook (exhaust before marking untestable)

`System.Diagnostics.Tracing.EventSource` is in the BCL on `net10.0`, so no `PackageReference` is
needed and this rule is expected to be straightforwardly testable. If it does not fire, work
through the standard playbook in AGENTS.md in order before concluding anything:

1. **Add a package reference** — not applicable; `EventSource` is in the BCL.
2. **Use stub types** — not applicable; the real `EventSource` is available.
3. **Pin `LangVersion=12`** — only if C# 13 overload routing appears to be redirecting the
   `WriteEvent` call.
4. **Set `ignore_internalsvisibleto=true`** — try this if the rule appears friend-assembly
   sensitive.
5. **Check `EnforceOnBuild`** in the analyzer source (`EnforceOnBuild.Never` is structurally silent
   at build).
6. **Check the reporting analyzer's assembly path** (`src/Features/` = IDE-only).
7. **Check the mscorlib gate** — rules asserting `System.String` lives in `mscorlib` cannot fire on
   `net10.0`.

Additionally, try adding an explicit `[EventSource(Name = "Test-MyEventSource")]` attribute to the
class — some EventSource analyzers only treat a type as an event source once it is fully shaped.

Only move the rule to `UntestableRules.cs` after exhausting all of the above.
